# 1. 현재 사이트 구조

## 1.1 코드와 운영 데이터

현재 YPL 사이트는 크게 두 부분으로 나뉩니다.

```text
GitHub / GitHub Pages
= 사이트 코드와 기본 데이터(SEED)

Supabase
= 실제 운영 중인 최신 공유 데이터
```

사이트 실행 시 `Supabase -> SEED` 순서로 데이터를 확인합니다.

```text
사이트 접속
  ↓
Supabase의 site_data / ypl_data_v4 조회
  ↓
데이터가 있으면 Supabase 데이터 사용
  ↓ 없으면
코드의 SEED 사용
```

따라서 GitHub 코드의 SEED와 실제 운영 사이트 데이터는 서로 다를 수 있습니다.

현재 확인된 대표 사례:

- GitHub SEED: 명예의 전당 5대 챔피언까지
- 실제 운영 사이트: 6대 챔피언까지 표시

즉 **Supabase의 `ypl_data_v4`가 현재 운영 데이터의 최신 원본**이고, SEED는 자동 백업본이 아닙니다.

## 1.2 테스트 사이트 주의사항

현재 `sjun27/ypl-site`의 production 빌드도 기존 운영 Supabase 프로젝트를 바라보고 있습니다.

따라서 테스트 GitHub Pages에서도 운영 데이터가 보입니다.

주의:

- 일반 조회: 가능
- Team Builder의 브라우저 로컬 저장: 운영 Supabase와 별개
- 공지/기록/대진표/칭호 등 관리자 저장 기능: **실제 운영 데이터에 영향을 줄 수 있음**

통계 시스템 실제 개발 전에 테스트용 Supabase 또는 별도 개발 환경 분리를 검토합니다.

# 2. 전체 제품 방향

YPL 사이트 기능은 크게 세 영역으로 구분합니다.

```text
YPL Tools
├─ 팀 빌더
└─ 배틀 데이터 (보류)

YPL 대회 운영
├─ 참가 / 엔트리
├─ 대진표
└─ 경기 결과

YPL 기록
├─ 트레이너 기록
├─ 대회 아카이브
├─ 포켓몬 기록
├─ 랭킹
├─ 칭호
└─ 명예의 전당
```

## 용어 구분

- **배틀 데이터**: Pokémon Champions 전체 환경의 포켓몬 메타/사용 통계
- **통계/기록**: YPL 내부 대회의 참가, 경기, 성적, 엔트리 데이터

두 시스템은 직접적인 데이터 의존관계가 없습니다.

# 3. Team Builder

## 상태: [진행]

현재 독립 Team Builder를 YPL 사이트에 통합한 상태입니다.

### 완료된 핵심

- Regulation 기반 팀 구성
- 포켓몬/도구/특성/기술/Stat Points 검증
- Species Clause / Item Clause 등 검증
- 팀 저장 및 작업 초안
- YPL Tools 메뉴 통합
- 현재 YPL 디자인에 맞춘 UI

### 다음 후보 기능

#### [설계] Pokémon Champions Replica Team ID Import

목표:

```text
Champions Team ID
  ↓
팀 데이터 조회
  ↓
YPL Team Builder 형식으로 변환
  ↓
Validation
  ↓
미리보기
  ↓
팀 불러오기
```

원칙:

- 기존 팀을 덮어쓰기 전 확인
- 외부 데이터가 불완전하면 조용히 삭제하지 않고 오류/경고 표시
- YPL 내부 canonical ID로 정규화
- 외부 resolver에 직접 종속되지 않도록 adapter 계층 사용

#### [설계] YPL 대회 엔트리 제출

장기적으로 Team Builder에서 구성한 팀을 대회 참가 엔트리로 제출할 수 있도록 연결합니다.

제출 이후에는 **제출 당시 팀을 스냅샷으로 고정**합니다.

개인 Team Builder에서 나중에 수정해도 과거 대회 엔트리는 바뀌면 안 됩니다.

# 4. Battle Data

## 상태: [보류]

여기서 말하는 Battle Data는 YPL 내부 통계가 아니라 **Pokémon Champions 전체 환경의 포켓몬 통계**입니다.

예시:

- 포켓몬 사용률
- 기술 채용률
- 도구 채용률
- 특성 채용률
- Stat Alignment
- 랭커 파티
- 시즌/Regulation별 메타

포케모음, PokeDB 등 이미 강한 전문 서비스가 존재하고, 데이터 수집/갱신 파이프라인 유지비용이 큽니다.

현재 판단:

- YPL의 고유성이 낮음
- 다른 전문 서비스가 대체 가능
- 데이터 원천 확보 및 유지보수 난이도가 높음
- 현재는 YPL 기록 시스템보다 우선순위가 낮음

따라서 독립 Battle Data 시스템은 당분간 보류합니다.

추후 검토 가능한 형태:

- Team Builder에서 외부 메타 페이지 연결
- 안정적인 공식/공개 API 확보 시 작은 메타 패널 제공
- YPL만의 명확한 분석 차별점이 생기면 독립 Tool로 재검토

# 5. YPL Records System

## 상태: [설계]

기존의 단순 `기록` 페이지를 **YPL 대회 역사 전체를 관리하는 Records System**으로 발전시킵니다.

이 시스템의 목적은 단순 통계 수치가 아니라 다음을 한곳에 연결하는 것입니다.

```text
대회
  ↓
Entry
  ↓
Match / Result
  ↓
트레이너 기록 / 대회 기록 / 포켓몬 기록
  ↓
칭호 / 명예의 전당
```

---

## 5.1 핵심 설계 원칙

### 원칙 A. 통계 숫자보다 원본 사실을 저장

다음처럼 결과 숫자를 직접 원본으로 저장하지 않습니다.

```text
이상준 = 18승 11패
망나뇽 = 14회
```

대신 다음 사실을 저장합니다.

- 누가 어떤 대회에 참가했는가
- 어떤 엔트리를 제출했는가
- 누가 누구와 경기했는가
- 누가 이겼는가
- 최종 대회 성적은 무엇인가

그 결과를 이용해 승패/승률/채용률 등을 계산합니다.

장점:

- 잘못 입력한 경기 결과를 고치면 통계도 같이 수정
- 시즌별/전체/싱글/더블 등 필터를 나중에 자유롭게 추가
- 칭호 조건을 다시 계산 가능

### 원칙 B. 과거 자료를 추측하지 않음

과거에는 전체 대진표가 없고 우승/준우승/4강만 남아 있을 수 있습니다.

이 경우 경기 승패를 역산하지 않습니다.

프로필에서는 다음처럼 구분합니다.

```text
대회 성적
= 남아 있는 옛 기록까지 포함

공식 경기 전적
= 실제 Match 데이터가 존재하는 시점부터 집계
```

필요하면 화면에 `공식 경기 전적은 YPL ○○ 시즌부터 집계` 문구를 표시합니다.

### 원칙 C. 통계를 위해 운영자에게 추가 입력을 요구하지 않음

현재처럼 대진표에서 승자를 누르는 행동 자체가 경기 기록 입력이어야 합니다.

```text
대진표에서 승자 선택
  ↓
Match 저장
  ↓
전적 자동 계산
```

통계를 위해 별도 엑셀이나 별도 결과 입력 작업을 만들지 않는 것을 목표로 합니다.

# 7. 트레이너 프로필

## 상태: [설계]

로그인용 프로필이 아니라 **YPL 대회 기록 기반 트레이너 카드**입니다.

예시:

```text
이상준
YPL Trainer

통산 대회 성적
참가 12회
우승 2회
준우승 1회
4강 4회

공식 경기 전적
18승 11패
승률 62.1%
최다 연승 5

※ 공식 경기 전적은 집계 가능한 시즌부터
```

추가 영역:

- 시즌별 성적
- 시즌별 경기 전적
- 최근 대회 이력
- 각 대회 등록 엔트리 6마리
- 보유 칭호
- 명예의 전당 이력
- Signature Pokémon
- 상대 전적 / Rival
- 최다 연승
- 선호 포맷

후반부의 재미 통계는 원본 Match/Entry가 충분히 쌓인 뒤 UI에 추가합니다.

# 9. 포켓몬 기록

## 상태: [설계]

목표는 경쟁 환경의 엄밀한 메타 통계가 아니라 **YPL에서 어떤 포켓몬이 어떻게 기록됐는지 보여주는 재미 요소**입니다.

초기 지표:

- 엔트리 등록 횟수
- 엔트리 채용률
- 사용 트레이너 수
- 우승 엔트리 포함 횟수
- 준우승 엔트리 포함 횟수
- 4강 이상 엔트리 포함 횟수
- 시즌별 기록
- 같이 많이 등록된 포켓몬
- 해당 포켓몬으로 주요 성적을 낸 트레이너

### 초기에는 포켓몬 승률을 만들지 않음

엔트리 6마리에 포함됐다고 실제 경기에서 선출된 것은 아니므로 `망나뇽 승률 65%` 같은 표시는 부정확합니다.

경기별 실제 선출 포켓몬까지 기록하는 시스템을 추후 도입할 경우 다시 검토합니다.

# 11. 대진표 연동

## 상태: [설계]

현재 대진표 코드는 이미 다음 형식을 지원합니다.

- 싱글 엘리미네이션
- 더블 엘리미네이션
- 조별리그 -> 본선
- 팀전

각 매치에는 `a`, `b`, `winner`가 존재하므로 기록 시스템과 연결하기 좋은 상태입니다.

### BYE

부전승은 실제 경기 승리로 집계하지 않습니다.

```text
Player vs BYE
= 다음 라운드 진출
≠ 공식 경기 1승
```

### 더블 엘리미네이션

Winner Bracket, Loser Bracket, Grand Final, Reset Final을 각각 실제 독립 경기로 계산합니다.

### 팀전

팀 전체 결과와 개인 대결 결과를 분리합니다.

```text
Team Match
├─ Player Match 1
├─ Player Match 2
├─ Player Match 3
└─ Ace Match
```

팀전 개인 경기를 통산 개인 전적에 포함할지는 대회 설정으로 결정할 수 있게 합니다.

# 12. 공식 전적 반영 여부

## 상태: [설계]

대회마다 다음 설정을 둘 수 있도록 검토합니다.

```text
공식 경기 전적 반영: ON / OFF
```

예시:

- 정규 파이컵: ON
- Champions: ON
- 팀전: 운영 규정에 따라 선택
- 파이컵 Light: 선택
- 단순 친선전: OFF

OFF여도 대회/엔트리/결과 기록 자체는 남깁니다.

# 14. 칭호 시스템

## 상태: [설계]

현재 칭호는 보유자 이름을 직접 관리하는 방식입니다.

새 시스템에서는 자동화 수준을 세 단계로 구분합니다.

### AUTO

원본 기록만으로 확정 가능한 칭호.

예:

- 첫 승
- 10승
- 첫 우승
- Champions 우승
- 루키 리그 우승

### REVIEW

엔트리/성적을 이용해 후보를 자동 발견하지만 운영진 확인이 필요한 칭호.

예:

- 같은 타입 엔트리로 4강 이상
- 특정 포켓몬으로 여러 차례 우승

### MANUAL

현재 시스템이 기록하지 않는 경기 내용 또는 특별 이벤트.

예:

- 한 마리도 쓰러지지 않고 우승
- 교체 없이 우승
- 특별 이벤트 칭호

목표는 전부 자동화하는 것이 아니라 **누락을 줄이고 자동화 가능한 부분만 안정적으로 자동화**하는 것입니다.

# 15. 명예의 전당

## 상태: [설계]

현재 명예의 전당은 챔피언 정보와 우승 엔트리를 별도 관리합니다.

향후:

```text
Champions 대회 종료
  ↓
우승자 확정
  ↓
명예의 전당 등록 후보 자동 생성
  ↓
운영진 확인
  ↓
명예의 전당 반영
```

으로 연결합니다.

과거 챔피언의 우승 엔트리도 가능한 범위에서 유지합니다.

# 16. 데이터 모델 초안

## 상태: [설계]

Supabase 실제 테이블 설계는 접근권한 확보 및 운영 데이터 백업 후 확정합니다.

현재 개념적으로 필요한 핵심 객체:

### Player

고유 트레이너 식별자.

이름 문자열만으로 연결하지 않고 `player_id`를 사용해 오타/동명이인/이름 변경 문제를 방지합니다.

### Season

시즌명, 시작일, 종료일.

### Tournament

대회명, 시즌, 날짜, 포맷, 부문, Regulation, 특수 룰, 팀전 여부, 공식 전적 반영 여부.

### Entry

한 트레이너가 한 대회에 참가한 기록.

### Entry Pokémon / Team Snapshot

대회 제출 당시 엔트리.

### Match

대회, 단계, 참가 Entry A/B, 승자 등 실제 경기 결과.

### Title Award

칭호 획득 이력 및 지급 방식(AUTO/REVIEW/MANUAL).

중요:

`18승 11패` 같은 계산 결과 자체를 핵심 원본으로 삼지 않습니다.

# 17. 과거 데이터 이관 원칙

## 상태: [설계]

과거 자료는 남아 있는 수준에 따라 다르게 처리합니다.

```text
full_match
= 전체 대진표가 있어 개별 승패 복원 가능

placement
= 우승/준우승/4강만 확인 가능

winner_only
= 우승자만 확인 가능

manual
= 운영진이 별도 자료로 확인한 기록
```

없는 기록을 추측해서 만들지 않습니다.

과거 성적/칭호/챔피언 엔트리는 가능한 만큼 보존하고, 전체 경기 전적과 포켓몬 엔트리 통계는 데이터가 신뢰 가능한 시점부터 집계합니다.

# 18. Supabase 작업 원칙

## 상태: [대기]

현재는 Supabase를 수정하지 않습니다.

진행 순서:

```text
1. 친구에게 Supabase Developer 접근권한 확보
2. 현재 site_data / ypl_data_v4 읽기
3. 최신 운영 데이터 원본 백업
4. 실제 데이터 인벤토리 작성
5. GitHub SEED와 차이 확인
6. Records System 데이터 모델 최종 확정
7. 테스트 환경에서 새 구조 검증
8. 운영 데이터에 점진적 적용
```

접근권한을 받았다고 바로 운영 DB를 수정하지 않습니다.

현재 `ypl_data_v4`는 여러 운영 데이터를 하나의 JSON으로 보관하고 있으므로 실수로 덮어쓰면 다른 기능에도 영향을 줄 수 있습니다.
