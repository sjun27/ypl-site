# 1. 현재 사이트 구조

## 1.1 코드와 운영 데이터

현재 YPL 사이트는 크게 두 부분으로 나뉩니다.

```text
GitHub / GitHub Pages
= 사이트 코드와 기본 데이터(SEED)

Supabase
= 실제 운영 중인 최신 공유 데이터
```

사이트 실행 시 `Supabase -> SEED` 순서로 데이터를 확인합니다.

```text
사이트 접속
  ↓
Supabase의 site_data / ypl_data_v4 조회
  ↓
데이터가 있으면 Supabase 데이터 사용
  ↓ 없으면
코드의 SEED 사용
```

따라서 GitHub 코드의 SEED와 실제 운영 사이트 데이터는 서로 다를 수 있습니다.

현재 확인된 대표 사례:

- GitHub SEED: 명예의 전당 5대 챔피언까지
- 실제 운영 사이트: 6대 챔피언까지 표시

즉 **Supabase의 `ypl_data_v4`가 현재 운영 데이터의 최신 원본**이고, SEED는 자동 백업본이 아닙니다.

Records 개발 과정에서 추가로 다음 차이를 확인했습니다.

- 로컬 SEED 클래식: 35회
- 운영 Supabase 클래식: 28회
- 운영에만 반영된 최신 회차도 일부 존재

따라서 로컬 기능 테스트에서는 기존 회차 수의 절대값보다 **반영 전후 변화량**을 기준으로 검증합니다. 운영 데이터 정합성 확인과 SEED 동기화는 Supabase 원본 백업 후 별도로 진행합니다.

## 1.2 테스트 사이트 주의사항

현재 `sjun27/ypl-site`의 production 빌드도 기존 운영 Supabase 프로젝트를 바라봅니다.

따라서 개인 GitHub Pages는 운영위원 내부 베타·조회용으로 사용할 수 있지만, 관리자 저장 기능은 실제 운영 데이터에 영향을 줄 수 있습니다.

현재 운영 원칙:

- 일반 조회 / UI 확인: 가능
- Team Builder의 브라우저 로컬 저장: 운영 Supabase와 별개
- 공지 / 기록 / 대진표 / 칭호 등 관리자 저장: 베타 Pages에서는 사용하지 않음
- 실제 저장 기능 테스트: localhost의 비운영 저장 경로에서 수행
- 별도 테스트용 Supabase는 현재 만들지 않음

운영·테스트 DB 분리는 실제 필요성이 생기면 재검토합니다.

# 2. 전체 제품 방향

YPL 사이트 기능은 크게 세 영역으로 구분합니다.

```text
YPL Tools
├─ 팀 빌더
└─ 배틀 데이터 (보류)

YPL 대회 운영
├─ 참가 / 엔트리
├─ 대진표
└─ 경기 결과

YPL 기록
├─ 트레이너 기록
├─ 대회 아카이브
├─ 포켓몬 기록
├─ 랭킹
├─ 칭호
└─ 명예의 전당
```

## 용어 구분

- **배틀 데이터**: Pokémon Champions 전체 환경의 포켓몬 메타/사용 통계
- **통계/기록**: YPL 내부 대회의 참가, 경기, 성적, 엔트리 데이터

두 시스템은 직접적인 데이터 의존관계가 없습니다.

# 3. Team Builder

## 상태: [진행]

현재 독립 Team Builder를 YPL 사이트에 통합한 상태입니다.

### 완료된 핵심

- Regulation 기반 팀 구성
- 포켓몬/도구/특성/기술/Stat Points 검증
- Species Clause / Item Clause 등 검증
- 팀 저장 및 작업 초안
- YPL Tools 메뉴 통합
- 현재 YPL 디자인에 맞춘 UI

### 다음 후보 기능

#### [설계] Pokémon Champions Replica Team ID Import

목표:

```text
Champions Team ID
  ↓
팀 데이터 조회
  ↓
YPL Team Builder 형식으로 변환
  ↓
Validation
  ↓
미리보기
  ↓
팀 불러오기
```

원칙:

- 기존 팀을 덮어쓰기 전 확인
- 외부 데이터가 불완전하면 조용히 삭제하지 않고 오류/경고 표시
- YPL 내부 canonical ID로 정규화
- 외부 resolver에 직접 종속되지 않도록 adapter 계층 사용

#### [설계] YPL 대회 엔트리 제출

장기적으로 Team Builder에서 구성한 팀을 대회 참가 엔트리로 제출할 수 있도록 연결합니다.

제출 이후에는 **제출 당시 팀을 스냅샷으로 고정**합니다.

개인 Team Builder에서 나중에 수정해도 과거 대회 엔트리는 바뀌면 안 됩니다.

# 4. Battle Data

## 상태: [보류]

여기서 말하는 Battle Data는 YPL 내부 통계가 아니라 **Pokémon Champions 전체 환경의 포켓몬 통계**입니다.

예시:

- 포켓몬 사용률
- 기술 채용률
- 도구 채용률
- 특성 채용률
- Stat Alignment
- 랭커 파티
- 시즌/Regulation별 메타

포케모음, PokeDB 등 이미 강한 전문 서비스가 존재하고, 데이터 수집/갱신 파이프라인 유지비용이 큽니다.

현재 판단:

- YPL의 고유성이 낮음
- 다른 전문 서비스가 대체 가능
- 데이터 원천 확보 및 유지보수 난이도가 높음
- 현재는 YPL 기록 시스템보다 우선순위가 낮음

따라서 독립 Battle Data 시스템은 당분간 보류합니다.

추후 검토 가능한 형태:

- Team Builder에서 외부 메타 페이지 연결
- 안정적인 공식/공개 API 확보 시 작은 메타 패널 제공
- YPL만의 명확한 분석 차별점이 생기면 독립 Tool로 재검토

# 5. YPL Records System

## 상태: [진행]

기존의 단순 `기록` 페이지를 **YPL 대회 역사 전체를 관리하는 Records System**으로 발전시킵니다.

이 시스템의 목적은 단순 통계 수치가 아니라 다음을 한곳에 연결하는 것입니다.

```text
대회
  ↓
Entry
  ↓
Match / Result
  ↓
트레이너 기록 / 대회 기록 / 포켓몬 기록
  ↓
칭호 / 명예의 전당
```

---

## 5.1 핵심 설계 원칙

### 현재 1차 구현 상태

새 Supabase 테이블을 만들기 전에 기존 `ypl_data_v4`를 읽는 1차 Records 계층을 구현했습니다.

현재 구현:

- `트레이너 / 대회 / 포켓몬 / 랭킹` 기록 UI
- 기존 회차 기반 과거 입상 기록
- YPL 시즌 3 이후 반영 완료 개인전·팀전 대진표 기반 Match 원본 보존 및 내부 통계 계산
- BYE 제외
- 팀전의 선발 대결 및 에이스 결정전 Match 원본 포함
- 반영 완료 대진표의 전체 참가자 최종 성적 자동 산출
- 대진표 엔트리 기반 포켓몬 기록
- 대진표 → 회차 / 랭킹 / 시즌 성적 반영
- 연결 기록 반영 취소 및 원복
- 기록 반영 완료 후 대진표 잠금

현재 구조는 **장기 데이터 모델의 최종형이 아니다.** Player / Entry / Match를 별도 Supabase 테이블로 분리하는 작업은 운영 데이터 백업 및 접근권한 확보 후 진행합니다.

### 원칙 A. 통계 숫자보다 원본 사실을 저장

다음처럼 결과 숫자를 직접 원본으로 저장하지 않습니다.

```text
이상준 = 18승 11패
망나뇽 = 14회
```

대신 다음 사실을 저장합니다.

- 누가 어떤 대회에 참가했는가
- 어떤 엔트리를 제출했는가
- 누가 누구와 경기했는가
- 누가 이겼는가
- 최종 대회 성적은 무엇인가

그 결과를 이용해 승패/승률/채용률 등을 계산합니다.

장점:

- 잘못 입력한 경기 결과를 고치면 통계도 같이 수정
- 시즌별/전체/싱글/더블 등 필터를 나중에 자유롭게 추가
- 칭호 조건을 다시 계산 가능

### 원칙 B. 과거 자료를 추측하지 않음

과거에는 전체 대진표가 없고 우승/준우승/4강만 남아 있을 수 있습니다.

이 경우 경기 승패를 역산하지 않습니다.

프로필에서는 다음처럼 구분합니다.

```text
대회 성적
= 남아 있는 옛 기록까지 포함

공식 경기 전적
= 실제 Match 데이터가 존재하는 시점부터 집계
```

필요하면 화면에 `공식 경기 전적은 YPL ○○ 시즌부터 집계` 문구를 표시합니다.

### 원칙 C. 통계를 위해 운영자에게 추가 입력을 요구하지 않음

현재처럼 대진표에서 승자를 누르는 행동 자체가 경기 기록 입력이어야 합니다.

```text
대진표에서 승자 선택
  ↓
Match 저장
  ↓
전적 자동 계산
```

통계를 위해 별도 엑셀이나 별도 결과 입력 작업을 만들지 않는 것을 목표로 합니다.

### 원칙 D. 원본 기록과 공개 지표를 분리

경기 결과는 향후 재계산·검증이 가능하도록 원본으로 보존하되, 계산 가능한 모든 개인 지표를 기본 화면에 공개하지는 않습니다.

현재 정책:

```text
내부 원본/계산 유지
- 경기별 승자·패자
- 상대
- 경기 단계
- 시즌 / 대회
- 승률·상대전적 등 파생 계산이 가능한 Match 데이터

기본 공개
- 확인 가능한 전체 참가
- 우승 / 준우승 / 4강 (팀전 포함)
- 대회 이력 및 최종 도달 성적
- 등록 엔트리
- 칭호
- 명예의 전당

기본 미노출
- 개인 승/패
- 개인 승률
- Rival / Head-to-Head
```

미노출은 Records 기본 UI에서 평가성 개인 지표를 전면 표시하지 않는다는 의미이며, Match 원본을 삭제한다는 의미가 아닙니다.

# 7. 트레이너 프로필

## 상태: [진행]

로그인용 프로필이 아니라 **YPL 대회 기록 기반 트레이너 카드**입니다.

기본 공개 방향:

```text
이상준
YPL Trainer

통산 대회 기록
참가 12회
우승 2회
준우승 1회
4강 4회

전체 대회 이력
- 싱글 엘리미네이션: 우승 / 준우승 / 4강 / 8강 / 16강 ...
- 더블 엘리미네이션: 우승 / 준우승 / 3위 / 4위 / 공동 순위
- 조별리그 + 본선: 본선 도달 성적 또는 조별리그 탈락
- 팀전: 팀 성적을 각 팀원의 기록에 포함

등록 엔트리
칭호
명예의 전당
```

기본 공개 영역:

- 시즌별 성적
- 최근 대회 이력
- 각 대회 등록 엔트리 6마리
- 보유 칭호
- 명예의 전당 이력
- Signature Pokémon(추후 검토)
- 선호 포맷(추후 검토)

경기별 승자·패자와 상대 정보는 YPL 시즌 3부터 원본으로 보존합니다. 다만 개인 승/패, 승률, Rival/상대전적, 연승 등 평가성이 강한 파생 지표는 기본 트레이너 프로필에 공개하지 않습니다.

챔피언스 시리즈는 대회 회차 편집에 저장된 `round` 값을 그대로 사용해 `챔피언스 시리즈 N회`로 표기합니다. `champ` 값은 챔피언스 시리즈 여부만 판단하며 별도 회차 번호를 계산하지 않습니다.

# 9. 포켓몬 기록

## 상태: [진행]

목표는 경쟁 환경의 엄밀한 메타 통계가 아니라 **YPL에서 어떤 포켓몬이 어떻게 기록됐는지 보여주는 재미 요소**입니다.

초기 지표:

- 엔트리 등록 횟수
- 엔트리 채용률
- 사용 트레이너 수
- 우승 엔트리 포함 횟수
- 준우승 엔트리 포함 횟수
- 4강 이상 엔트리 포함 횟수
- 시즌별 기록
- 같이 많이 등록된 포켓몬
- 해당 포켓몬으로 주요 성적을 낸 트레이너

### 초기에는 포켓몬 승률을 만들지 않음

엔트리 6마리에 포함됐다고 실제 경기에서 선출된 것은 아니므로 `망나뇽 승률 65%` 같은 표시는 부정확합니다.

경기별 실제 선출 포켓몬까지 기록하는 시스템을 추후 도입할 경우 다시 검토합니다.

# 11. 대진표 연동

## 상태: [진행]

현재 대진표 코드는 이미 다음 형식을 지원합니다.

- 싱글 엘리미네이션
- 더블 엘리미네이션
- 조별리그 -> 본선
- 팀전

각 매치에는 `a`, `b`, `winner`가 존재하므로 기록 시스템과 연결하기 좋은 상태입니다.

### 현재 1차 대진표 연동

현재 legacy JSON 구조에서는 대진표 자체의 Match graph를 원본 경기 사실로 사용합니다.

대회 종료 후 `기록에 반영` 시:

```text
대진표
  ↓
대회 회차 생성
  ↓
누적 랭킹 / 시즌 성적 반영
  ↓
recordMeta로 연결 정보 보존
```

`반영 취소` 시 연결된 회차와 랭킹·시즌 증감을 함께 원복합니다.

반영이 완료된 대진표는 읽기 전용으로 잠그며, 결과 수정이 필요하면 먼저 반영 취소를 해야 합니다. 이는 Records가 읽는 대진표 결과와 반영된 회차가 우발적으로 불일치하는 것을 방지합니다.

별도 `Match` 테이블로의 정규화는 Phase D에서 진행합니다.

### BYE

부전승은 실제 경기 승리로 집계하지 않습니다.

```text
Player vs BYE
= 다음 라운드 진출
≠ 공식 경기 1승
```

### 더블 엘리미네이션

Winner Bracket, Loser Bracket, Grand Final, Reset Final을 각각 실제 독립 경기로 계산합니다.

### 팀전

팀 전체 결과와 개인 대결 결과를 분리합니다.

```text
Team Match
├─ Player Match 1
├─ Player Match 2
├─ Player Match 3
└─ Ace Match
```

팀전의 선발 대결과 에이스 결정전도 Match 원본에 포함합니다. 다만 개인 승/패·승률 등 평가성 파생 지표는 기본 공개하지 않으므로, 개인전과 팀전은 내부 데이터에서 구분 가능한 상태로 보존합니다.

# 12. Match 기록 범위와 향후 공식 전적 정책

## 상태: [설계]

YPL 시즌 3부터 반영 완료 개인전·팀전 대진표의 실제 Match 원본을 보존합니다.

- 실제 상대가 있는 경기만 Match로 보존
- BYE는 경기에서 제외
- 팀전은 선발 대결 및 에이스 결정전을 개별 Match로 보존
- Match에는 개인전/팀전 구분을 유지
- 개인 승/패·승률은 기본 공개하지 않음
- 반영 완료 대진표의 모든 참가자에 대해 최종 대회 성적을 자동 산출

향후 내부 통계나 특별 콘텐츠에서 필요하면 대회별로 다음 설정을 둘 수 있습니다.

```text
공식 경기 전적 반영: ON / OFF
```

예시:

- 정규 파이컵: ON
- Champions: ON
- 팀전: 운영 규정에 따라 선택
- 파이컵 Light: 필요 시 결정
- 단순 친선전: OFF

OFF여도 대회·엔트리·Match 원본 자체는 보존할 수 있습니다.

개인 승/패·승률을 기본 공개하지 않기로 했으므로 파이컵 Light의 공식 전적 포함 여부는 당장 운영 전제조건이 아닙니다.

# 14. 칭호 시스템

## 상태: [설계]

현재 칭호는 보유자 이름을 직접 관리하는 방식입니다.

새 시스템에서는 자동화 수준을 세 단계로 구분합니다.

### AUTO

원본 기록만으로 확정 가능한 칭호.

예:

- 첫 승
- 10승
- 첫 우승
- Champions 우승
- 루키 리그 우승

### REVIEW

엔트리/성적을 이용해 후보를 자동 발견하지만 운영진 확인이 필요한 칭호.

예:

- 같은 타입 엔트리로 4강 이상
- 특정 포켓몬으로 여러 차례 우승

### MANUAL

현재 시스템이 기록하지 않는 경기 내용 또는 특별 이벤트.

예:

- 한 마리도 쓰러지지 않고 우승
- 교체 없이 우승
- 특별 이벤트 칭호

목표는 전부 자동화하는 것이 아니라 **누락을 줄이고 자동화 가능한 부분만 안정적으로 자동화**하는 것입니다.

# 20. 아직 결정하지 않은 항목

## [완료] 공식 경기 전적 집계 시작점

공식 경기 승패는 **YPL 시즌 3부터** 집계합니다.

시즌 1~2 및 그 이전 기록은 우승/준우승/4강 등 확인 가능한 대회 성적만 보존하며 경기 승패를 역산하지 않습니다.

## [검토] 파이컵 Light의 공식 전적 반영 여부

Light도 대회·엔트리·Match 원본은 보존합니다. 개인 승/패·승률을 기본 공개하지 않기로 했으므로, Light를 향후 내부 '공식 전적' 범위에 포함할지는 필요할 때 결정합니다.

## [검토] 팀전 개인전의 통산 기록 반영 여부

팀전 형식 및 향후 규정에 따라 결정합니다.

## [검토] 포인트 랭킹 장기 유지 방식

현재 60/40/20 기반 포인트 시스템은 유지하되, 새로운 경기 전적/프로필과 별개의 지표로 관리합니다.

## [완료] 개인 승패·승률 공개 정책

YPL 시즌 3부터 경기별 승자·패자와 상대 Match 원본은 계속 기록합니다.

다만 트레이너 기본 공개 화면에는 개인 승/패, 승률, Rival/상대전적을 표시하지 않습니다. 참가·입상·엔트리·칭호·명예의 전당처럼 참여와 성취를 보여주는 정보를 중심으로 공개합니다.

## [완료] 챔피언스 시리즈 트레이너 이력 표기

챔피언스 시리즈도 대회 회차 편집에 저장된 `round` 값을 회차 번호의 source of truth로 사용합니다. `champ` 표시가 있으면 같은 `round` 값을 `챔피언스 시리즈 N회` 형식으로 보여주며 날짜순 재계산이나 별도 회차 번호 생성은 하지 않습니다. 트레이너 이력에서는 별도 배경색이나 강조 보더 없이 작은 `CHAMPIONS SERIES` 키커와 제목 위계로 일반 회차와 구분합니다.

## [완료] Records 메뉴의 1차 구조

`트레이너 / 대회 / 포켓몬 / 랭킹` 구조를 적용했습니다.

기존 누적 랭킹과 시즌별 성적은 `랭킹` 내부에 유지하며, 대회 회차 표시는 기존 운영 사이트의 시각 형식을 유지합니다.

## [완료] 기록 반영 후 대진표 잠금

대진표를 기록에 반영한 뒤에는 승자 선택, 팀전 결과, 엔트리 수정, 본선 재생성, 삭제를 막습니다.

수정이 필요한 경우:

```text
반영 취소
→ 연결 기록 원복
→ 대진표 수정
→ 다시 기록 반영
```

순서로 처리합니다.

## [검토] 대진표 연동 회차의 직접 편집 정책
